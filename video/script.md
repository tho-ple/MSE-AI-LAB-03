# Video narration script — Lab 03 (4 minutes)

Narration for `video/presentation.md`, written for **Kokoro TTS**.

How to use:

- Feed **only the text inside each ```text block```** to Kokoro, one audio file
  per scene. Never feed the headings or these notes.
- Scene 0 is the title block at the top of `presentation.md`; Scene N matches
  the heading `Scene N` there.
- Spelling is phonetic on purpose ("pie pea eye" = PyPI, "O S V" = OSV,
  "deps dot dev" = deps.dev, "my pie" = mypy). Numbers are written as spoken.
- The narration states that the voice is synthetic. Keep that sentence.

---

## Scene 0 — Title and team (≈ 20 s)

```text
This is our group video for lab three, concurrent dependency intelligence. The voice is generated by a text to speech model; the work and the evidence are ours. Johann built package A, Michael package B, and Thomas package C, and also merged everything.
```

## Scene 1 — Mission and method (≈ 30 s)

```text
Our service takes exact Python dependencies and asks three sources at once: pie pea eye for the latest version, O S V for vulnerabilities, and deps dot dev for licenses and dependencies. It returns one report, even when a source fails.

We started from the specification: about sixty traced requirements, twelve recorded decisions, three tickets, and a merge log.
```

## Scene 2 — The cut (≈ 25 s)

```text
We split the work for independence, not equal size. Package A took pie pea eye and O S V, package B took deps dot dev, and package C took the cache and the scanner. No package imports another package's code, so all three branches merged without a single code conflict.
```

## Scene 3 — Acceptance criterion three (≈ 35 s)

```text
Acceptance criterion three demands that all three sources start before any of them finishes. The scanner runs them in one task group, and deps dot dev runs its two calls in a second one. A test gate only opens once every call has started. At runtime, every fixture call sleeps two seconds. One package needs four calls, so sequential work would take eight seconds. We measured two point one.
```

## Scene 4 — Ownership (≈ 30 s)

```text
Every concurrency concern has one owner. One semaphore per scanner limits packages. A single flight shares one load between identical requests. A task group inside that load runs the sources. Only that load writes to the cache, and only complete results. On cancellation, every task group cancels and awaits its children.
```

## Scene 5 — Cache and partial failure (≈ 40 s)

```text
The same request twice: the first is a miss, the second a hit, twenty two milliseconds, and zero new upstream calls.

When O S V returns five oh three, the report is still H T T P two hundred, status partial. The other data stays, vulnerabilities is null, and one retryable failure names O S V. It is not cached. Null means unknown, never safe.
```

## Scene 6 — Quality gate and one diff (≈ 30 s)

```text
Ruff, the formatter, and strict my pie all pass, with fifty nine green tests. Our code review found one gap: a source that cancels itself would abort the whole scan. With decision twelve, only a real cancellation propagates. A faulty source now becomes one failure, and the report survives.
```

## Scene 7 — Acceptance decision (≈ 30 s)

```text
Our decision: accept, with a stated limitation. All ten acceptance criteria have tests and runtime evidence. The remaining risk: we only tested deterministic fixtures. Real services have rate limits and might spell versions differently than our strict identity check expects. Thank you for watching.
```
